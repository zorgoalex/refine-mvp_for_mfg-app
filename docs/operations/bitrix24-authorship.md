# Авторство заявок и оплат Bitrix

ERP хранит два разных факта: технический исполнитель записи (`created_by` / `edited_by`) и автор действия в Bitrix. Сервисный пользователь интеграции остаётся техническим исполнителем; его роль и возможность входа не меняются.

## Что отображается

| Запись | Источник автора | Где смотреть |
| --- | --- | --- |
| CRM-заявка | `crm.item.get.createdBy`, не `assignedById` | Входящие заявки → карточка → «Создал в Bitrix» |
| Заказ из CRM-заявки | Автор исходной заявки | Заказ → Финансы → Оплаты из Bitrix |
| Оплата через виджет | Подтверждённый `user.current` пользователя виджета, не администратор установки | Оплаты заявки, финансы заказа, карточка перенесённого платежа ERP |
| Штатная оплата Bitrix | Создатель неизвестен; `empPaidId` показывает только пользователя изменения статуса | Те же карточки; подпись «Статус оплаты изменил (Bitrix)» |

Имя дополняется ID Bitrix. Сопоставление с пользователем ERP показано отдельно и не меняет права доступа. Без имени остаётся ID; без ID отображается неизвестный автор. Имена выводятся обычным текстом. Это сведения API, а не гарантия личного действия человека: возможны роботы и интеграции.

Авторство в финансах доступно при `orders.view_financials` **и** `bitrix24.requests.view`, внутри существующей области доступа CRM. Финансовые права без CRM-просмотра по-прежнему дают доступ к суммам, но не к новым сведениям об авторах. Общий запрос заказа не выдаёт авторство Bitrix. В служебной информации заказа используются минимальные подписи технического автора ERP без обращения к `/users/86`.

## Обновление окружения

1. Доставить коммит в нужную ветку обычным workflow. Production обновляется из `main`, тестовый контур — из `feat/backend-erp-stage1`. Не собирать из общего незакоммиченного дерева.
2. Перед production-миграциями сделать и проверить backup через `ops/backup-prod-packet.sh` по [основному runbook](../deployment-and-operations.md#production-backup).
3. Из обновлённого checkout выполнить проверку миграций. Каждая команда ниже — одна строка; `$PG_CID` должен указывать на PostgreSQL нужного окружения, не на backend.

```bash
bash ops/apply-migrations.sh auto --detect-only --container "$PG_CID"
```

На актуальной базе новая ожидаемая миграция — `156_bitrix24_authorship.sql`. Если видны другие неприменённые миграции, проверить их отдельно перед запуском общего apply.

```bash
bash ops/apply-migrations.sh apply --container "$PG_CID" --to 156 --yes
```

```bash
bash ops/apply-migrations.sh probe 156_bitrix24_authorship.sql --container "$PG_CID"
```

Миграция добавляет три nullable-поля; существующие финансовые записи не меняет. На shared test server все тяжёлые команды, включая миграции, запускать через `rtk nice -n 10 /home/ovhtest/.codex/rtk-heavy-guard -- …`.

4. Пересобрать/recreate **только backend** стандартной командой используемого Compose и обновить frontend. Новых `.env`/Compose-переменных, ключей или переустановки виджета не требуется. Проверить `/health/live`, `/health/ready` и точный SHA.
5. Существующие заявки получат автора при следующей обработке сделки обратной синхронизацией. Кнопка сверки платежей обновляет сведения штатных оплат; массовая выгрузка заново не нужна. Не менять имя сделки только ради получения автора.
6. Старые команды виджета уже содержат достоверный ID автора; историческое имя задним числом не выдумывается. Новые команды сохраняют имя при первоначальном создании, повтор команды его не заменяет.

## Проверка

- Создать тестовую заявку в Bitrix под сотрудником, отличным от ответственного; проверить отдельные подписи автора и ответственного.
- Внести тестовую оплату через виджет под сотрудником, отличным от администратора установки. Проверить его имя/ID.
- Преобразовать тестовую заявку в заказ и явно перенести выбранный платёж. Автор должен сохраниться; повторный перенос не увеличивает сумму.
- Проверить пользователя с финансовыми правами без `bitrix24.requests.view`: новых сведений об авторах быть не должно.
- Открыть заказ с техническим автором интеграции: нет запроса `/api/v1/users/86`; показан «Сервис интеграции ERP».
- Ошибка `user.get` не должна блокировать импорт; остаётся ID. Права `user_basic` поддерживаются официальным методом. При отсутствии доступа проверить scopes установленного приложения; не давать пользователям права администратора ради подписи.

## Откат

Вернуть предыдущие backend/frontend образы стандартным workflow. Новые nullable-колонки оставить: предыдущий код их игнорирует. Не удалять оплаты, маппинги, сервисного пользователя и снимки для отката отображения.

# Товары и услуги

Самостоятельный справочник продаваемых позиций, не производственных деталей.

## Работа в приложении

1. Откройте `/catalog-items` в приложении или **Данные → Товары и услуги** (в старом меню — **Справочники**).
2. Нажмите **Создать позицию**. Заполните название, тип и единицу измерения.
3. Артикул, базовая цена и описание необязательны. Артикул уникален без учёта регистра, включая архив. Пустая цена означает «не задана», `0` — нулевую цену. Валюта — KZT.
4. В блоке **Служебные поля**: `1C_key` — необязательный UUID записи 1С, уникальный среди всех позиций, включая архив; **Порядок сортировки** — целое число от −32768 до 32767, по умолчанию100. Ключ вручную переносится из 1С, автоматически не генерируется; само поле обмен с 1С не включает.
5. Сохраните. Для изменения откройте **Изменить**; выключите **Активен**, чтобы архивировать. Для восстановления выберите фильтр **Архив**, откройте карточку и включите активность.
6. В сохранённой карточке отображаются ID, версия, кто создал/изменил и обе даты. Их заполняет сервер; ручное изменение запрещено. Даты показываются в часовом поясе браузера. Список упорядочен по порядку сортировки, названию, ID; поиск также находит по `1C_key`.

Физического удаления нет. Цена справочная: сохранение не меняет существующие заказы и платежи. Детали производства не изменяются.

Просмотр: `references.view` или `references.manage`. Изменения: `references.manage`, активный пользователь ERP (не service account). Название роли само по себе права не даёт.

При конфликте версии форма сохраняет введённое; **Загрузить версию** заменит черновик только после подтверждения. При неизвестном результате сетевого запроса поля блокируются: **Проверить повтором** повторяет ту же команду с тем же ключом. Не открывайте вторую форму для повторного создания той же позиции.

## API и хранение

`GET /api/v1/catalog-items`, `/units`, `/:id`; `POST /api/v1/catalog-items`; `PUT /api/v1/catalog-items/:id`. Полная схема — `backend/contracts/04-api-contract.openapi.yaml`.

Команды требуют `Idempotency-Key`, изменения — также `expectedVersion`. Идентичный повтор возвращает сохранённый ответ. Другой actor/ID/body с прежним ключом —409. Успешная команда, аудит и outbox атомарны; no-op не меняет версию и не добавляет бизнес-событие. Поля каталога не пишутся через Hasura.

`catalog_items` хранит позиции; `catalog_item_commands` — подтверждения выполненных команд. Подтверждения пока хранятся бессрочно, чтобы не создавать дубли поздними повторами; API для их просмотра/очистки нет. События `catalog.item_created|updated|archived|restored` пишутся в аудит и общий outbox. Новых отправителей уведомлений/правил не добавлено.

## Обновление окружения

1. Проверить точный commit, pending-список миграций и отсутствие чужих изменений. Миграции: `157_products_services_catalog.sql`, затем `161_catalog_reference_service_fields.sql`.
2. Через существующий `ops/apply-migrations.sh` применить миграцию и проверить её end-state probe. Она добавляет две таблицы и индексы, не заполняет каталог примерами и не меняет `units`.
3. Собрать backend с новым SHA, обновить существующий сервис backend обычным Compose окружения; дополнительные Compose-файлы или переменные не нужны.
4. Дождаться frontend того же SHA. Проверить health/live, health/ready, затем список единиц/позиций и создание→изменение→архив→восстановление тестовой позиции.
5. Проверить чтение без прав и запрет сохранения с правом только просмотра. В production не создавать тестовые оплаты/заказы ради проверки каталога.

Rollback каталога: additive-таблицы оставить; destructive down-миграции нет. После включения импорта Bitrix нельзя вслепую возвращать старый backend при активной синхронизации или виджете: он не содержит новых финансовых защит и может заменить строки сделки итоговой строкой ERP. Требуется совместимый проверенный образ либо отдельно согласованная остановка соответствующих записей по incident-процедуре runbook. Production обновляется только после отдельного разрешения.

## Сопоставление с товарами Bitrix24

Администраторы интеграции (право `bitrix24.integration.manage` плюс чтение/управление справочниками) ведут точные сопоставления **товар Bitrix24 → позиция каталога** в `/bitrix24/incoming-requests` — панель «Настройки интеграции», блок «Товары Bitrix → позиции справочника».

- Сопоставление всегда по числовому ID товара Bitrix24 — подбора по названию нет. ID можно выбрать из уже виденных товаров или ввести вручную, если товар ещё не появлялся в заявках.
- Позиция каталога выбирается поиском через каталог; повторяющиеся названия различаются по артикулу и ID. Неактивная сохранённая позиция остаётся видимой.
- Сохранение использует версию сопоставления: конфликт версии не теряет черновик — **Обновить список** применяет чужое изменение только после подтверждения.
- При сверке заявки товарные строки сделки переносятся в строки каталога заявки с ценой Bitrix24 (цена уже включает скидку и НДС — повторно они не применяются). Без активного сопоставления импортированные строки блокируют оплату и конвертацию заявки до исправления.
- Импортированные строки заявки не редактируются вручную и меняются только сверкой; локально введённые позиции остаются редактируемыми.

API: `GET /api/v1/bitrix24/product-mappings`, `PUT /api/v1/bitrix24/product-mappings/:bitrixProductId`, `POST /api/v1/bitrix24/incoming-requests/:requestId/reconcile`. Полная схема — `backend/contracts/04-api-contract.openapi.yaml`.

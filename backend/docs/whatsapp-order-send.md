# Отправка заказа в WhatsApp из карточки заказа

Под иконкой «Отправить заказ» в шапке карточки заказа (слева от «⋯») есть команды:
- «Отправить клиенту в WhatsApp» — на личный номер клиента заказа;
- «Отправить в чат «…»» — по одной команде на каждый чат из настроек;
- «Отправить сотруднику «…»» — по одной на каждого сотрудника из настроек.

В подменю выбирается форма заказа. Отправка начинается сразу, без подтверждения.

Модуль: `backend/src/modules/whatsapp/order-send/`. Миграция: `230_whatsapp_order_send.sql`.

## Формы

Реестр форм — `order-send.types.ts` (`ORDER_FORMS`). Файл собирает backend из данных заказа; браузер
файлы не передаёт.

| Код | Название | Файл | Цены |
|---|---|---|---|
| `production_pdf` | PDF для производства | PDF | нет |
| `order_pdf` | PDF заказа | PDF | да |
| `production_excel` | Excel для производства | XLSX | нет |
| `order_excel` | Excel заказа | XLSX | да |
| `production_image` | Изображение для производства | PNG (страницы) | нет |
| `order_image` | Изображение заказа | PNG (страницы) | да |

- **Excel** собирает тот же построитель, что и кнопка Excel в карточке
  (`src/utils/excel/orderExcelBuilder.ts`), на том же шаблоне.
  - Backend хранит точные копии построителя (`forms/shared/`) и шаблона
    (`backend/assets/order-forms/order_template.xlsx`).
  - Тест `shared-copy.test.ts` сверяет копии побайтно.
  - После правки исходника скопируйте файл заново.
- **PDF** рисует pdfkit (`forms/pdf-form.ts`) раскладкой бланка заказа. Шрифты — Liberation Sans из
  `backend/assets/fonts`. «Для производства» группирует детали по плёнке.
- **Изображения** (`forms/image-form.ts`) — вид листа Excel-шаблона заказа: шапка (заказ, № присадки,
  заказчик, общая сумма; фрезеровка/обкат/плёнка, материал, остаток, срок; дата, конструктор, телефон,
  площадь, кол-во деталей), сетка деталей с жёлтыми «Примечание»/«Пленка», пустая строка между плёнками;
  итоги — в шапке. Числа и строки — из `forms/form-layout.ts` (как у PDF). SVG → PNG через `@resvg/resvg-js`
  (`renderAsync`, вне event loop), ширина 1400 px. По **70 деталей** на картинку, «стр. k/N»; полные
  страницы одной высоты, последняя обрезана по содержимому. Больше 20 картинок — `ORDER_SEND_TOO_LONG`.
  «Для производства» — без цены, суммы, остатка и телефона клиента.
- **Формы без цен** получают проекцию без цен, сумм, скидки, платежей и остатка, даже если
  отправитель видит финансы. В Excel режим без цен не пишет платежи (O–Q).
- **Новая форма** = запись в `ORDER_FORMS` + генератор в `forms/index.ts` + расширение CHECK кодов
  форм в миграции.

## Настройки

Конфигурация → «Рассылка сообщений» → «Отправка заказа из карточки». Право `whatsapp.manage`.

| Настройка | Значение |
|---|---|
| Включено | По умолчанию выключено. |
| Порог частоты | 1–1440 минут, по умолчанию 1. Общий на всю систему: начала доставок из карточек — не чаще раза в N минут. |
| Окно отправки | 0 … половина порога, минуты (по умолчанию 0). Следующая доставка уходит в случайный момент окна после порога: при пороге 10 и окне 5 — через 10–15 минут после предыдущей. Случайная задержка выбирается один раз в момент доставки (`next_delivery_at`), смена порога или окна перевыбирает её от последней доставки. |
| Клиенту | Разрешённые формы и шаблон подписи. Пустой список — пункт клиенту не показывается. |
| Чаты | До 20 чатов. У каждого: группа, название в меню, формы, подпись. |
| Сотрудники | До 20. У каждого: сотрудник (в выборе — «логины / ФИО», без рабочего телефона — с пометкой), канал (WhatsApp; Telegram — следующий этап, сейчас `422 ORDER_SEND_CHANNEL_UNSUPPORTED`), формы, подпись. Поле `employees` в PUT необязательно: клиент прошлого релиза его не шлёт, и список не меняется. |

Ключ чата (`chatKey`) живёт, пока не меняется группа. Смена группы или удаление чата архивирует строку
(`archived_at`) и отменяет поставленную в очередь отправку в неё (`recipient_removed`). Новая группа
получает новый ключ. Строки чатов не удаляются: группа неизменяема (триггер), история ссылается на ключ.

Ключ сотрудника (`recipientKey`, `whatsapp_order_send_employees`) живёт, пока не меняются сотрудник и
канал; смена или удаление архивирует строку и отменяет ожидающие отправки (`recipient_removed`).

Выключение отменяет отправку, стоящую в очереди (`disabled`).

Переменные подписи: `{order_name}`, `{client}`, `{order_date}`, `{completion_date}`, `{form}`.

## Права

| Действие | Права |
|---|---|
| Меню и отправка | `orders.view` и `orders.export`, каждое в своём scope (`all` / `own` / `assigned`) |
| Формы с ценами | дополнительно `orders.view_financials` |
| Настройки | `whatsapp.manage` |

Меню (`GET /whatsapp/order-send/menu`) не содержит ID групп, а формы с ценами в нём показываются только
пользователю с финансами.

## Команда `POST /api/v1/orders/:orderId/whatsapp-sends`

1. Доступ к заказу (view + export в scope).
2. Журнал идемпотентности (`actor_id`, `idempotency_key`):
   - тот же ключ с тем же заказом, получателем и формой → прежний ответ, даже если с тех пор
     выключили отправку, сменили телефон или WhatsApp недоступен;
   - другое тело → `IDEMPOTENCY_KEY_REUSED`.
3. Транзакция:
   - блокировки `whatsapp_broadcast_control` FOR SHARE → настройки FOR UPDATE;
   - журнал ещё раз;
   - проверки: пауза, включено, лимиты очереди (`ORDER_SEND_QUEUE_FULL`: 100 всего, 20 у автора),
     та же форма тому же получателю уже ждёт (`ORDER_SEND_ALREADY_QUEUED` с `sendId`, `estimatedAt`),
     чат, разрешённая форма, финансы, телефон;
   - чтение заказа FOR SHARE, сборка файла (страниц), запись в хранилище, строка `queued` (страницы
     2..N — в `whatsapp_order_send_parts`), аудит `requested` с местом и «≈ когда».
   - Порог частоты команда **не проверяет**: отправка всегда встаёт в общую очередь (FIFO), ответ несёт
     `position` и `estimatedAt`. Старый backend (до миграции 233) отказывал `ORDER_SEND_ACTIVE` /
     `ORDER_SEND_COOLDOWN` — frontend эти коды по-прежнему понимает.
4. **Повтор после неизвестного результата.** Если последняя отправка того же заказа тому же
   получателю той же формой закончилась `unknown`, команда отказывает `ORDER_SEND_PREVIOUS_UNKNOWN`
   (`details.sendId`). Повтор проходит только с `confirmAfterUnknown` = этот `sendId` — карточка
   спрашивает «Отправить ещё раз?». Проверка идёт под блокировкой настроек, поэтому вкладки
   браузера не могут её обойти.
5. Отказ пишет отдельную строку аудита `whatsapp.order_send.refused` и техническую запись. Телефона и
   ID группы в них нет.

## Телефон клиента

- **Выбор номера** — как в экспорте заказа: основной номер клиента, иначе наименьший.
- **Разбор номера** (`order-send-phone.ts`):
  - основной номер выделяется до удаления форматирования;
  - добавочный или второй номер после разделителя (`-`, `,`, `;`, `/`, «доб.», «вн.») отбрасывается;
  - результат — `7XXXXXXXXXX`;
  - всё остальное — `CLIENT_PHONE_INVALID`.
- **Chat id** (`@c.us` или `@lid`) worker узнаёт через WAHA `check-exists` прямо перед отправкой.
  Номера нет в WhatsApp — `failed / CLIENT_NOT_ON_WHATSAPP`, порог не тратится.
- **Где виден телефон.** В аудите, журнале и ответах API — только маска `7701***2060`. Технический
  журнал WAHA пишет путь без query.

- **Выбор телефона в карточке.** `GET /api/v1/orders/:orderId/whatsapp-sends/client-contacts` отдаёт телефоны
  клиента этого заказа, на которые можно отправить (читаемые, без повторов; только маски; основной первым).
  Если их несколько, в меню «Отправить заказ» у клиента — подменю телефонов; команда получает
  `target: {kind: 'client', phoneId}`. Без `phoneId` действует правило по умолчанию (основной, иначе наименьший).
  Телефон другого клиента или удалённый — `409 CLIENT_PHONE_MISSING`.
- **Один получатель — «клиент + номер».** Защиты от дубля в очереди и от повтора после неизвестного исхода
  считают получателем клиента на конкретном номере (`recipient_fingerprint`, как у сотрудника): тот же номер,
  выбранный явно или по умолчанию, — тот же получатель; другой номер клиента — другой. Отправка, сделанная до
  появления отпечатков, считается тем же получателем, если ушла на этот номер или её номер уже очищен.
- **Без перенаправления.** Перед отправкой worker проверяет выбранный телефон (`client_phone_id`): он всё ещё
  принадлежит клиенту заказа и читается как тот же номер; иначе отмена `recipient_changed`. Смена основного
  телефона выбранный номер не затрагивает.
- **Метка номера.** Меню показывает маску номера и выдаёт с ней непрозрачную метку (`token`); команда с
  выбранным телефоном обязана вернуть её (`phoneToken`). Если строку телефона изменили после показа меню, метка
  не совпадёт — `409 ORDER_SEND_PHONE_CHANGED`, карточка перечитывает телефоны; на невиданный номер отправка не
  уйдёт. Для телефонов сотрудника — то же (`contactToken`; без метки от старого интерфейса — как раньше).
- **Единственный читаемый телефон не по умолчанию** (например, основной номер нечитаем) предлагается как
  выбранный (`isDefault=false`), а не как отправка по умолчанию.
- **Окончательный отказ.** Отказ «получатель уже не тот, что выбран» (`ORDER_SEND_PHONE_CHANGED`,
  `ORDER_SEND_PHONE_CHOICE_UNAVAILABLE`, `CLIENT_PHONE_MISSING`, `EMPLOYEE_CONTACT_MISSING`,
  `ORDER_SEND_RECIPIENT_UNKNOWN`, `ORDER_SEND_CHAT_UNKNOWN`) записывается по ключу команды
  (`whatsapp_order_send_refusals`) в той же транзакции под общей блокировкой и возвращается с `details.final =
  true`. Любой следующий запрос с этим ключом — запоздавший, повторный, после возврата номера или смены релиза —
  получает тот же отказ и никогда отправку. Интерфейс сбрасывает ожидающую команду только по отказу с этой
  отметкой. Запись отказа хранится бессрочно, как ключ принятой отправки (данных получателя в ней нет), и
  пишется вместе с событием аудита `whatsapp.order_send.refused` одной транзакцией. Выбранный телефон, ставший
  нечитаемым, — тоже `ORDER_SEND_PHONE_CHANGED`.
- **Выкладка.** Миграция **237** (колонка `client_phone_id` без проверок и таблица окончательных отказов;
  аддитивна, прежний backend её не замечает) → backend K2a → backend K2b. K2a — тот же код с выключенным
  `ORDER_SEND_CLIENT_PHONE_CHOICE`: ставит отпечаток и защиты «клиент + номер», перепроверяет и доставляет
  строки с выбранным телефоном, разбирает и **повторяет** уже принятые команды с выбранным телефоном, но новых
  не создаёт (окончательный отказ `ORDER_SEND_PHONE_CHOICE_UNAVAILABLE`) и телефонов на выбор не отдаёт; он же —
  цель отката. Откат K2b → только на K2a; на backend до K2a после использования выбора телефона не
  откатываться (его защита после неизвестного исхода смотрит на последнюю отправку клиенту на любой номер).

## Сотрудник как получатель

- **Контакты** — `employee_work_contacts` (телефон/email/Telegram, по одному основному на тип); правятся
  только командой `PUT /api/v1/employees/:id/contacts` (`employees.manage`) с версией набора
  (`employees.work_contacts_version`) и аудитом `employee.work_contacts.updated` — только маски, примечание
  длиной. Сотрудника с контактами нельзя удалить напрямую (RESTRICT) — его деактивируют.
- **Команда** `target: {kind: 'employee', recipientKey, contactId?}`: без `contactId` — основной телефон,
  с ним — этот телефон сотрудника. Отказы: `ORDER_SEND_RECIPIENT_UNKNOWN`, `ORDER_SEND_CHANNEL_UNSUPPORTED`,
  `EMPLOYEE_INACTIVE`, `EMPLOYEE_CONTACT_MISSING`.
- **Отпечаток получателя** `recipient_fingerprint = sha256(соль + employee:id:телефон)` (соль —
  `whatsapp_order_send_settings.identity_salt`, наружу не отдаётся) держит защиты от дубля и от повтора
  после неизвестного исхода и после очистки телефона через 7 дней.
- **Перед отправкой** worker перепроверяет под блокировками: строка получателя не в архиве, тот же
  сотрудник и канал, сотрудник активен, выбранный контакт — всё ещё тот же телефон. Любое изменение —
  отмена (`recipient_removed` / `recipient_changed`), отправка никогда не перенаправляется на другой номер.
  Номера нет в WhatsApp — `failed / EMPLOYEE_NOT_ON_WHATSAPP`.
- **Аудит** отправки связан с сотрудником (`relatedEntities: employee`); аудит пользователя — с прежним и
  новым связанным сотрудником.

## Заявка поставщику из экрана снабжения

Текст заявки поставщику уходит через ту же очередь, тот же порог частоты, журнал, отмену и хранение, что и
формы заказа; у такой отправки нет заказа (`order_id IS NULL`, `target_kind = 'supplier'`,
`form_code = 'supplier_text'`).

- **Включение:** настройка «Отправлять заявки поставщикам в WhatsApp» (`supplier_requests_enabled`, по умолчанию
  выключена) при включённой отправке из карточки. Выключение отменяет ожидающие заявки (`disabled`).
- **Права:** `procurement.view` + `procurement.manage` и полный scope заявки — все её заказы, включая удалённые
  (то же правило, что у команд заявки). Проверяется в команде и ещё раз перед доставкой.
- **Получатель:** поставщик справочника по ключу заявки — `s:<id>` или `c:<uuid>` (единственный поставщик с этим
  `ref_key_1c`); ключ-название (`n:`) и «не указан» — отказ `SUPPLIER_NOT_LINKED`. Телефон — контакт
  `supplier_contacts` вида `phone`.
- **Меню** `GET /api/v1/procurement/supplier-requests/:id/whatsapp-menu`: поставщик, его телефоны как маски с
  непрозрачными метками (`token`), причина недоступности (`disabled`, `release`, `not_linked`, `no_phone`,
  `supplier_inactive`, `status`).
- **Команда** `POST /api/v1/procurement/supplier-requests/:id/whatsapp-sends`
  `{text, edited, templateId, templateVersion, textVersion, contactId, contactToken, idempotencyKey,
  confirmAfterUnknown?}`:
  - текст — ровно тот, что в окне «Текст для поставщика» (шаблон и ручные правки); backend его не строит. Не пуст,
    не длиннее 20 000 символов, без управляющих символов (кроме перевода строки и табуляции) — иначе 422
    `SUPPLIER_SEND_TEXT_INVALID`;
  - `textVersion` — версия заявки, по которой построен текст, должна равняться текущей;
  - `contactId` и `contactToken` обязательны всегда (и для основного телефона): номер не выбирается «по умолчанию
    на момент команды»;
  - статус заявки — `draft` или `sent`; команда статус не меняет.
- **Разбиение** (`supplier-send-text.ts`): сообщения до 4096 символов, граница — по переводу строки; строка
  длиннее сообщения режется по пробелу, без пробелов — по символам. Не больше 8 сообщений. Первое сообщение
  хранится в строке отправки (`text_body`), остальные — в `whatsapp_order_send_parts`.
- **Окончательные отказы** (`details.final`, запись в `whatsapp_order_send_refusals` вместе с аудитом, бессрочно):
  `SUPPLIER_REQUEST_VERSION_CONFLICT`, `SUPPLIER_REQUEST_NOT_SENDABLE`, `SUPPLIER_NOT_LINKED`, `SUPPLIER_INACTIVE`,
  `SUPPLIER_CONTACT_MISSING`, `ORDER_SEND_PHONE_CHANGED`, `SUPPLIER_SEND_UNAVAILABLE`. Повтор запроса с тем же
  ключом получает тот же отказ, что бы ни изменилось.
- **Тот же получатель:** эта заявка + этот поставщик на этом номере (`recipient_fingerprint`) + этот текст
  (`text_sha256`). Тот же текст ждёт — `ORDER_SEND_ALREADY_QUEUED`; прежняя закончилась `unknown` — нужно
  подтверждение (`confirmAfterUnknown`); другой текст — новая отправка.
- **Перед доставкой** worker под блокировками проверяет: настройка включена; автор активен, с обоими правами и
  полным scope; заявка существует, в статусе `draft|sent`, и её содержимое прежнее — отпечаток
  `request_content_sha256` (ключ поставщика, срок, комментарий, строки: ресурс, количество, единица, порядок);
  ключ ведёт к тому же поставщику, он активен; контакт — тот же номер. «Отметить отправленной» отправку не
  отменяет (содержимое не меняется). Расхождение — `cancelled`: `request_changed`, `recipient_changed`,
  `recipient_removed`, `permission_revoked`, `disabled`. Номера нет в WhatsApp — `failed /
  SUPPLIER_NOT_ON_WHATSAPP`.
- **Доставка:** сообщения `sendText` подряд, без повторов; первое не ушло — как для файла; первое ушло, а
  следующее нет — `unknown / PARTIAL_DELIVERY` (`partsSent` в аудите и событии). Порог тратится один раз.
- **Порядок блокировок** (команда и worker): `control → settings → строка отправки → автор (FOR SHARE) → заявка
  (FOR SHARE) → заказы заявки (FOR SHARE, по возрастанию id) → поставщик (FOR SHARE) → контакты`. Команды
  заявки берут `автор → заявка FOR UPDATE` и не трогают таблицы WhatsApp; команды заказов не блокируют заявку.
- **Аудит:** `whatsapp.supplier_send.<requested|intent|sent|failed|unknown|cancelled|expired|refused>`, связи
  `supplier_request` и `supplier`; без номера, метки и текста — маска, длина и sha256 текста, признак ручной
  правки.
- **События (outbox):** `whatsapp.supplier_send.<requested|sent|failed|unknown|cancelled|expired>`, агрегат
  `whatsapp_supplier_send`, в транзакции перехода, ключ `whatsapp_supplier_send:<sendId>:<переход>`; в payload —
  `supplierRequestId`, `supplierId`, `orderIds`, автор, request id.
- **Хранение:** через 7 дней текст отправки и всех её частей очищается одной транзакцией вместе с телефоном и
  `provider_message_id`; остаются статус, маска, длина и sha256 текста.

## Доставка (worker)

Отправки ждут в общей очереди и уходят по одной: за шаг — самая старая `queued` с наступившим
`next_attempt_at` (отложенная из-за недоступности WAHA может пропустить вперёд следующую). Worker
работает только при `relayOwner=in_process`; шаг — раз в 15 секунд и сразу после команды. Форму,
которой этот backend не знает (отправка более новой версии), он не отправляет:
`failed / ORDER_SEND_FORM_UNSUPPORTED`, слот не тратится.

Перед отправкой, под блокировкой настроек, worker перепроверяет:
- текущие права отправителя (view, export, финансы — по ролям из БД);
- что чат на месте, его группа совпадает с сохранённой, а форма разрешена;
- для клиента — что форма разрешена, заказ у того же клиента, а выбранный телефон тот же.

Любое расхождение → `cancelled` с причиной. Отправка никогда не перенаправляется.

Порог доставки (delivery gate):
- если `now` раньше `max(last_delivery_at + порог, next_delivery_at)`, отправка ждёт (`next_attempt_at`);
- иначе `last_delivery_at = now`, `next_delivery_at = now + порог + random(0..окно)` — слот тратится в
  начале попытки и не возвращается.

Все ожидающие стоят на одном гейте; при его наступлении первой уходит старшая.

«≈ когда» (`order-send-queue.ts`, `estimateQueue`) повторяет worker: от гейта каждая следующая отправка
на `порог + окно/2` позже; отправка, срок которой кончится раньше её очереди, слот не занимает
(`mayExpire`).

Итог попытки (`sendFile` для файла):

| Результат | Состояние |
|---|---|
| ответ с непустым id сообщения | `sent` |
| ответ без id, таймаут, 5xx | `unknown`, без повтора |
| явный отказ WAHA (400, 404, 405, 415, 422, 501) | `failed` (`WAHA_REJECTED` / `WAHA_FILE_UNSUPPORTED`) |

Изображения уходят `sendImage` подряд, подпись — у первой страницы, без повторов страниц:
- все страницы с id → `sent`;
- первая не ушла → как для файла (`failed` / `unknown`);
- первая ушла, а следующая нет или её исход неизвестен → `unknown / PARTIAL_DELIVERY` (`partsSent` в
  аудите); повтор этой формы этому получателю — только с подтверждением.

Восстановление и очередь:
- строка `sending` старше `BACKEND_WHATSAPP_RELAY_STALE_LOCK_MS` → `unknown` (`PROCESS_LOST_AFTER_INTENT`);
- «Остановить все рассылки» останавливает и эти отправки: строка ждёт;
- отправка ждёт в очереди не больше **24 часов** от команды, затем `expired`; смена порога или окна
  будит ожидающие (перепланирование), но срок не продлевает.

## Отмена и журнал очереди

- `POST /api/v1/whatsapp/order-send/sends/:sendId/cancel`: автор — свою, `whatsapp.manage` — любую;
  чужая для остальных — 404. `queued` → `cancelled / manual` (`cancelled_by`, аудит с отменившим и
  `relatedUserId` = автор); завершённая возвращается как есть; `sending` → 409
  `ORDER_SEND_NOT_CANCELLABLE`.
- `GET /api/v1/whatsapp/order-send/queue` (`whatsapp.manage`): все ожидающие с местом и «≈ когда»;
  `history=1` — завершённые за 7 дней, по 50. Только маски получателей.
- UI: Конфигурация → «Рассылка сообщений» → «Очередь отправок из карточки»; автор отменяет свои
  ожидающие под колокольчиком.

## Хранение

- Файлы лежат в `<WHATSAPP_DAILY_DIGEST_DIR>/order-sends/` (своя блокировка): 10 МиБ на файл,
  512 МиБ на каталог. При заполнении — `ORDER_SEND_STORAGE_FULL`.
- Через 7 дней у завершённых отправок удаляются файл, ID группы, телефон и `provider_message_id`
  (в нём бывает номер). Остаются статус, маска и `provider_ack`.
- Файлы без ссылки старше часа (откат команды после сбоя) удаляются при очистке.
- Страницы 2..N изображений очищаются вместе со своей отправкой (файл и `provider_message_id`).

## Выкладка и откат

### Заявка поставщику (миграция 238 → K3a → K3b)

- **Порядок:** миграция **238** (аддитивная, при работающем прежнем backend: новые nullable-колонки, `order_id`
  допускает NULL, изменённые CHECK пересоздаются `NOT VALID` и проверяются отдельно, без блокировки приложения)
  → backend **K3a** (этот же код с `ORDER_SEND_SUPPLIER_REQUESTS = false`) → backend **K3b**.
- **K3a** новых отправок заявок не создаёт (окончательный отказ `SUPPLIER_SEND_UNAVAILABLE`, меню —
  `unavailableReason: 'release'`), но принятые команды повторяет, существующие строки читает, перепроверяет,
  доставляет, отменяет, истекает и очищает — с тем же аудитом и событиями.
- **Откат K3b → только на K3a:** выключить «Отправлять заявки поставщикам» (отменит ожидающие), остановить K3b,
  запустить K3a. На backend до K3a после появления строк `supplier` не откатываться. Схема 238 остаётся; ручного
  SQL нет.

### Сотрудники-получатели (шаги C → 235 → D)

- **Порядок:** backend C (совместимый: не доставляет цель `employee`, а переводит её в
  `failed / ORDER_SEND_TARGET_UNSUPPORTED`; читает историю сотрудника) → миграция **235** (при работающем C) →
  backend D. Без схемы 235 backend D не запускать.
- **Откат D → только на C** (не ниже): выключить отправку в настройках (отменит очередь, в том числе отправки
  сотрудникам) или удалить сотрудников из настроек (`recipient_removed`), остановить D, запустить C. Прерванную
  доставку C переведёт в `unknown` штатным восстановлением со связью с сотрудником. Ожидающие строки `employee`,
  оставшиеся в очереди, C завершит `failed / ORDER_SEND_TARGET_UNSUPPORTED` без WhatsApp. Схема 235 остаётся;
  ручного SQL нет. Новый FE на C скрывает контакты и пункты сотрудников.

### Очередь и картинки (шаги A → 233 → B, история)

- **Два шага.** A — совместимый backend без миграции (читает незнакомые формы, чистит PNG и страницы,
  не доставляет незнакомые формы); B — миграция **233** (снимает «одна активная», `manual`,
  `cancelled_by`, формы-картинки, `parts_total`, `whatsapp_order_send_parts`) и этот backend.
  Миграции аддитивны и идут при работающем backend; новый backend — после миграции.
- **Проверка до включения на production:** пробная отправка PDF, XLSX и изображения в тестовую группу
  и на свой номер (`sendFile` и `sendImage` установленной WAHA).
- **Откат B → только на A:** выключить отправку в настройках (отменит очередь), остановить B, запустить
  A. Прерванную доставку A переведёт в `unknown` штатным восстановлением (с аудитом). Ручного SQL нет.
  На прежний backend без шага A после отправок изображений не откатываться (он не чистит PNG и не читает
  новые формы).

## «Мои отправки»: балуны и время под колокольчиком

`GET /api/v1/whatsapp/my-sends` отдаёт отправки текущего пользователя за последние 24 часа (до 30):
- из карточки — по `actor_id`;
- из календаря — по `initiated_by_user_id`.

Отдельного права не нужно: видны только свои отправки. ID групп и телефоны в ответ не попадают,
только заголовок вида «Заказ 230725 → клиенту, PDF заказа».

`estimatedAt` — примерное начало доставки для ожидающих отправок:
- карточка — `max(сейчас, next_attempt_at, max(порог, выбранный момент окна))`;
- календарь — `max(сейчас, ближайшее сообщение, порог календаря до начала доставки)`.

Frontend (`src/components/whatsapp/`):
- колокольчик опрашивает `my-sends` каждые 15 с, пока есть ожидающие отправки; в течение 30 минут
  после активности — раз в минуту; иначе только по сигналу «поставлено в очередь» из карточки или
  календаря;
- завершение отправки, которую видели ожидающей, показывает полупрозрачный балун внизу справа на
  15 с с крестиком;
- ожидающие отправки показываются блоком «WhatsApp: ожидают отправки» в выпадающем списке
  колокольчика.

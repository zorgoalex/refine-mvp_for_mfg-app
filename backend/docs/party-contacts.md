# Контакты поставщиков, производителей и клиентов; связь поставщика и клиента с контрагентом 1С

## Контакты

У поставщика и производителя — блок «Контакты»: телефоны, email, аккаунты Telegram; у каждого вида один
«основной» (первый контакт вида становится основным сам). У клиента телефоны остаются в списке телефонов клиента
(`client_phones`, прежние правила), а блок контактов хранит email и Telegram.

| Владелец | Таблица | Виды | Чтение | Изменение |
|---|---|---|---|---|
| Поставщик | `supplier_contacts` | phone, email, telegram | `suppliers.view` | `suppliers.manage` |
| Производитель | `vendor_contacts` | phone, email, telegram | `vendors.view` | `vendors.manage` |
| Клиент | `client_contacts` | email, telegram | `clients.view` | `clients.update` |

- `GET /api/v1/{suppliers|vendors|clients}/:id/contacts` — набор и его версия.
- `PUT …/contacts {version, contacts[]}` — замена набора целиком: версия сравнивается под блокировкой строки
  владельца (`FOR NO KEY UPDATE`), контакт с `contactId` сохраняет id, отсутствующие удаляются. Конфликт версии —
  `409 PARTY_CONTACTS_VERSION_CONFLICT`; неверное значение или вид — `422 PARTY_CONTACT_INVALID`; повтор —
  `422 PARTY_CONTACT_DUPLICATE`.
- `GET /api/v1/supplier-contacts?ids=`, `GET /api/v1/vendor-contacts?ids=` — контакты для колонки списка.
- Версия набора лежит в `party_contact_versions` (нет строки = 0). Строка владельца командой **не обновляется**:
  не меняются `updated_at`/`edited_by`, у клиента не срабатывает CRM-синхронизация.
- Нормализация: телефон → `7XXXXXXXXXX`, email → нижний регистр, Telegram → без `@`.
- Аудит: `supplier.contacts.updated`, `vendor.contacts.updated`, `client.contacts.updated` — только маски
  значений, примечание длиной, связь с владельцем.
- Владельца с контактами нельзя удалить напрямую (`ON DELETE RESTRICT`) — его деактивируют.
- Миграция **236** переносит прежнее поле «Телефон» поставщика в основной телефон набора, если оно читается как
  номер; само поле остаётся в таблице и видно в «Просмотре» как «Телефон (прежнее поле)».

## Связь поставщика с контрагентом 1С

`suppliers.ref_key_1c` меняется только командами backend (в правах Hasura колонка исключена из insert и update):

- `GET /api/v1/supplier-counterparties?search=` — контрагенты для выбора: зеркало 1С (не папки, не помеченные на
  удаление, присутствующие в источнике; поставщики первыми), иначе контрагенты из документов снабжения, иначе
  пусто. У каждого — уже связанный поставщик, если есть.
- `GET /api/v1/suppliers/:id/counterparty` — текущая связь.
- `PUT /api/v1/suppliers/:id/counterparty {refKey1c|null, expectedRefKey1c|null}` — привязать, сменить, снять.
  Текущий ключ сравнивается с `expectedRefKey1c` под блокировкой: расхождение — `409
  SUPPLIER_COUNTERPARTY_CONFLICT` (в `details.refKey1c` — текущее значение); ключ уже равен новому — повтор без
  второго аудита. Контрагент другого поставщика — `409 SUPPLIER_COUNTERPARTY_TAKEN`; неизвестный ключ — `422
  SUPPLIER_COUNTERPARTY_UNKNOWN`. Аудит `supplier.counterparty_linked|unlinked`.
- `POST /api/v1/suppliers/from-counterparty {refKey1c}` — добавить контрагента в справочник (имя контрагента +
  ключ); идемпотентно по ключу. Поставщик с таким названием уже есть — `409 SUPPLIER_NAME_TAKEN`
  (`details.supplierId`): его привязывают командой выше. Аудит `supplier.created_from_counterparty`.

**Эффект привязки:** загрузчик документов 1С на ближайшем проходе проставит `supplier_id` всем документам
контрагента — разовая волна новых ревизий документов; то же при смене и снятии ключа. Ключи заявок и документов
снабжения (`c:<ключ>`) и `resource_suppliers` не меняются.

## Сопоставление клиента с контрагентом 1С

`clients.ref_key_1c` — ключ контрагента 1С, с которым сопоставлен клиент: у клиента один контрагент, у контрагента
один клиент (уникальный индекс `idx_clients__ref_key_1c`). Меняется только командой backend; в формах клиента поля
больше нет, в правах Hasura колонка исключается из insert и update скриптом
`ops/hasura/clients-backend-owned-columns.sh`.

- `GET /api/v1/clients/:id/counterparty` (`clients.view`) — текущая связь: `refKey1c`, `available` (контрагенты 1С
  загружены) и `counterparty` — название, код, БИН/ИИН, признак покупателя, телефоны. `counterparty = null` при
  заданном ключе и `available = true` значит: контрагента с таким ключом в загруженных данных 1С нет (удалён или
  помечен на удаление).
- `GET /api/v1/clients/:id/counterparty-candidates?search=` (`clients.update` — поиск открывает весь справочник
  контрагентов 1С с БИН/ИИН и телефонами, поэтому только тем, кто вправе сопоставлять) — контрагенты для выбора: не папки, не
  помеченные на удаление, присутствующие в источнике. С `search` — по названию, коду, БИН/ИИН или цифрам телефона
  (до 50). Без `search` — похожие на клиента (до 10), с причиной в `matchedBy`: `name` — то же имя (без кавычек и
  слов ТОО/ИП/…), `phone` — тот же номер (последние 10 цифр), `similar` — похожее имя (pg_trgm, от 0.45). У каждого —
  клиент, с которым он уже сопоставлен, если есть.
- `PUT /api/v1/clients/:id/counterparty {refKey1c|null, expectedRefKey1c|null}` (`clients.update`) — сопоставить,
  заменить, снять. Текущий ключ сравнивается с `expectedRefKey1c` под блокировкой строки клиента: расхождение —
  `409 CLIENT_COUNTERPARTY_CONFLICT` (`details.refKey1c` — текущее значение); ключ уже равен новому — повтор без
  второго аудита. Контрагент другого клиента — `409 CLIENT_COUNTERPARTY_TAKEN` (`details.clientId`,
  `details.clientName`); ключа нет в загруженных данных 1С или данные не загружены — `422
  CLIENT_COUNTERPARTY_UNKNOWN` (снять сопоставление можно и без данных 1С). Два клиента, одновременно выбирающие
  одного контрагента, выстраиваются в очередь (advisory lock по ключу).
- Аудит: `client.counterparty_linked` (сопоставление и замена) и `client.counterparty_unlinked`; сущность и
  связанная сущность — клиент (`related_client_id`), до/после — ключ и название контрагента, в metadata — код и
  БИН/ИИН.
- Команда меняет в строке клиента только ключ и `edited_by`; обновление строки ставит обычную CRM-синхронизацию
  клиента в очередь.
- Массовое подтверждение (кнопка «Сопоставить с 1С» в списке клиентов, `clients.update`):
  - `GET /api/v1/client-counterparty-matches` — активные клиенты без контрагента и их точные кандидаты (то же имя
    или тот же телефон). `matches` — пары без разночтений в обе стороны: у клиента ровно один точный кандидат, он
    свободен и не подходит другому несопоставленному клиенту; сила пары `both` (имя и телефон), `phone`, `name`.
    `ambiguous` — клиенты, у которых кандидатов несколько, кандидат общий с другим клиентом или уже занят: их
    сопоставляют в карточке. `summary` — счётчики. Похожие имена (pg_trgm) здесь не участвуют.
  - `POST /api/v1/client-counterparty-matches/confirm {pairs: [{clientId, refKey1c}]}` (до 100 пар, клиент и
    контрагент — по одному разу) — каждая пара выполняется как обычная команда сопоставления клиента без
    контрагента: своя транзакция, своя запись аудита `client.counterparty_linked` с `metadata.via = bulk_confirm`.
    Пара, которая стала невозможной, не прерывает остальные: в `results` её статус `conflict` (у клиента уже другое
    сопоставление), `taken` (контрагент у другого клиента, с держателем), `unknown`, `not_found`, `uncertain`
    (неожиданная ошибка пары: обычно транзакция откатилась, но при сбое на подтверждении фиксации связь могла
    записаться). Запрос нельзя повторять вслепую после потерянного ответа: пара — это команда с ожидаемым состоянием
    «контрагента нет», и повтор вернул бы связь, которую за это время сняли в карточке. Поэтому интерфейс после
    потерянного ответа и для пар `uncertain` ничего не отправляет повторно, а читает текущую связь каждого такого
    клиента (`GET /clients/:id/counterparty`). Подтверждением служит только найденная связь с тем же ключом —
    тогда пара «сопоставлена». Чтение, которое связи не нашло, ничего не доказывает (запись могла ещё выполняться:
    сервер дорабатывает запрос или база завершает фиксацию) — такая пара, как и пара, состояние которой прочитать не
    удалось, показывается как «результат неизвестен», с именем клиента и ссылкой в карточку. «Пропущено» говорится
    только по определённому отказу сервера. Следующие части после потерянного ответа не отправляются. Интерфейс заранее
    отмечает только пары `both` и шлёт запросы частями.
- Команда — единственный писатель колонки. Импорт заказа (snapshot) ключ клиента не записывает: существующему
  клиенту связь не меняет (в том числе снятую не возвращает), нового создаёт без контрагента; ключ из snapshot
  используется только чтобы найти уже существующего клиента.

Выкладка: backend → frontend → права Hasura (`ops/hasura/clients-backend-owned-columns.sh`, после того как новый
frontend в работе: прежняя форма клиента ещё отправляет `ref_key_1c`). Миграций нет. Frontend без backend блок
скрывает. Откат прав — `--revert`.

## Выкладка и откат

Порядок обязателен: миграции 236 и 242 → backend → frontend → права Hasura
(`ops/hasura/suppliers-backend-owned-columns.sh`).
Frontend раньше backend выкладывать нельзя: прежние поля «Phone» и «Ref Key 1C» в форме поставщика уже убраны, а
новые блоки без backend скрыты. Миграция 236 только создаёт таблицы и переносит телефон поставщика в его
основной контакт; идёт при работающем backend. Права `suppliers` меняет точечный скрипт
`ops/hasura/suppliers-backend-owned-columns.sh` — только списки колонок insert/update, с проверкой версии metadata
(если metadata изменили после чтения, ничего не применяется); `--dry-run` показывает по ролям «было → станет».
Откат прав — `--revert`; таблицы остаются. Откат
backend — по правилу отправок WhatsApp (`whatsapp-order-send.md`, «Выкладка и откат»): прежний backend допустим,
только если после остановки нового backend журнал окончательных отказов пуст и нет отправок нового вида; иначе —
совместимый образ того же релиза.

**Прежнее поле «Телефон» поставщика (миграция 242).** Между миграцией 236 и новым frontend прежняя форма (и
вкладки, оставшиеся открытыми) ещё пишет `suppliers.phone`. Триггер `trg_supplier_phone_contact_sync` держит
телефонный контакт поставщика равным этому полю, **пока набор контактов поставщика ни разу не сохраняли командой**
(нет строки в `party_contact_versions`): тот же номер — контакт и его id не меняются, другой — заменяется,
нечитаемое значение — контакт убирается. После первого сохранения набора контакты принадлежат пользователю и поле
на них больше не влияет. Миграция один раз выравнивает то, что успели записать до неё.

Изменение через прежнее поле — тоже ревизия набора: триггер увеличивает `party_contact_versions.version`, оставляя
строку с `saved_by_command = false`. Форма, прочитавшая набор до такого изменения, получает от команды 409
`PARTY_CONTACTS_VERSION_CONFLICT` и перечитывает набор (телефон не теряется). Признак `saved_by_command` ставит
триггер `trg_party_contact_versions_saved`: прямая запись версии (команда контактов любого релиза backend) —
`true`, запись из синхронизации — `false`; backend колонку не называет.

# Входящие сигналы

## Назначение

Отдельный экран `/inbound-signals` показывает ключевые сообщения и результат действий ERP.
Это не технический аудит WhatsApp и не очередь личных автоответов.
Первый адаптер — входящие групповые сообщения WhatsApp; Telegram и другие каналы пока не подключены.
Принимаются текст и подпись вложения. Файлы не скачиваются, OCR не выполняется.

## Настройка

1. В «Конфигурация → Обработка сообщений → Источники» добавить имя сессии WAHA и ID доверенной группы (`…@g.us`). Включить источник.
2. В «Сигналы» добавить стабильный код, например `goods.ready`, и название «Заказ готов».
3. В «Поиск заказа» добавить шаблон: префикс `заказ`, формат «цифры», поле «Внутренний ID заказа». Для названия заказа, ID раскроя и кода проекта есть отдельные варианты.
4. В «Ключевые слова» связать источник, сигнал и шаблон. Например, ключевое слово `готов`, исключение `не готов`, режим «Целые слова». Включить правило и сохранить все настройки.
5. Проверить пример `Заказ 1254 готов` в блоке проверки текста. Это не создаёт сигналов и не меняет статусы; существование заказа проверяется при реальном приёме.
6. В правилах автостатусов выбрать событие «Входящий сигнал» (`message.signal_detected`), добавить условие «Код входящего сигнала — один из»: `goods.ready`, затем нужное действие/статус. Остальные условия работают как прежде.

**Доверие:** любой участник подключённой группы может создать сигнал. Подключать только рабочие доверенные группы. Сообщения, отправленные самим привязанным аккаунтом, игнорируются. Личные сообщения обслуживаются прежним механизмом WhatsApp-правил.

Все различные коды сигналов создаются независимо. Несколько совпавших правил с одинаковым кодом создают один сигнал с сохранением списка правил. Исключения проверяются перед ключевыми словами.
Если шаблон находит несколько идентификаторов, каждый должен однозначно указывать на один и тот же заказ. Проект/раскрой с несколькими заказами требует ручного выбора; массового изменения нет.
Идентификаторы после префикса не содержат пробелов; для названий с пробелами используйте внутренний ID. Пользовательские регулярные выражения и SQL запрещены.

## Работа с журналом

- Понятный режим включён по умолчанию. Технический режим доступен отдельным правом.
- Фильтры: дата, канал, код источника, код сигнала, заказ, состояние, текст.
- Автообновление раз в 15 секунд только при видимой странице; есть ручное обновление и время последней успешной загрузки. Ошибка обновления показывается явно.
- «Нужно уточнить заказ»: найти заказ → проверить действия → подтвердить привязку. Изменившийся заказ/правила/конфигурация потребуют нового предпросмотра.
- Ложные совпадения исключаются с причиной. Повтор доступен только для окончательной ошибки; успешно обработанный сигнал нельзя переназначить или повторить.
- Сообщения без ключевых слов видны только пользователям с правом разбора при включении соответствующего переключателя.

## Права

| Право | По умолчанию |
|---|---|
| `message_signals.view` | admin, superadmin, top_manager, manager |
| `message_signals.resolve` | admin, superadmin, top_manager |
| `message_signals.technical` | admin, superadmin |
| `message_signals.manage_config` | admin, superadmin |

Матрица ролей управляет правами. Просмотр связанных сигналов дополнительно требует `orders.view` и текущий scope доступа к заказу. Менеджер не видит чужие/неразобранные сообщения, включая поиск и счётчики.

## Исполнение и хранение

- Миграция `173_inbound_signals.sql`: конфигурация, квитанции дедупликации, сообщения, сигналы/очередь, шаги, квитанции команд.
- Приём после HMAC-проверки существующего WhatsApp webhook. Только включённые источники и сообщения новее момента включения источника. Включение не импортирует старую переписку.
- Дедупликация по SHA-256 от канала/подключения/чата/исходного message ID, не по тексту и не по ID доставки webhook.
- Очередь: до 10 сигналов за тик 10 секунд; claim-token + `SKIP LOCKED`; 5 попыток с минутной задержкой; восстановление зависшей обработки через 5 минут.
- Автостатусы, бизнес-аудит, outbox и завершение задания коммитятся одной транзакцией. Исполнитель — системный actor с `user_id=null`, без административных пользовательских прав.
- Все тексты, авторы, подробные шаги и квитанции ручных команд живут 90 дней. Истёкшие сообщения сразу скрыты API; очистка удаляет до 500 сообщений за час. Хеш-квитанции остаются для защиты от поздней повторной доставки.
- Постоянный аудит/outbox содержит внутренние ID и результаты, но не текст, подпись, сырой webhook, ID чата, автора или исходного сообщения.
- Изменение конфигурации отправляет старые ожидающие сигналы на ручную проверку. Отключённый источник не исполняет очередь. Повтор ручного сигнала сохраняет утверждённый fingerprint предпросмотра.

## Production rollout (выполняет оператор)

Точный release SHA должен включать этот документ, миграцию и код. Не использовать старый WhatsApp SHA как доказательство наличия новой функции.

1. Чистый checkout `main`, подтверждённый release SHA и свежий проверенный backup packet через `ops/backup-prod-packet.sh`.
2. Подключить **оба** env-файла: `.env` и `backend-release.env` при проверке Compose. В production Compose пробросить:

```yaml
BACKEND_ENABLE_INBOUND_SIGNALS: ${BACKEND_ENABLE_INBOUND_SIGNALS:-false}
BACKEND_INBOUND_SIGNALS_RELAY_OWNER: ${BACKEND_INBOUND_SIGNALS_RELAY_OWNER:-none}
```

3. Проверить миграции перед запуском новой версии. Применить только отсутствующие зависимости и `173_inbound_signals.sql` штатным `ops/apply-migrations.sh`. Пример (имя контейнера заранее проверить):

```bash
ops/apply-migrations.sh status --container erp_test-postgresdb-1
ops/apply-migrations.sh apply --to 173 --container erp_test-postgresdb-1
ops/apply-migrations.sh probe 173_inbound_signals.sql --container erp_test-postgresdb-1 \
  && echo 'Migration: OK' || echo 'STOP: проверить миграцию, не продолжать deploy'
```

4. Для первого запуска `.env`: `BACKEND_ENABLE_INBOUND_SIGNALS=true`, `BACKEND_INBOUND_SIGNALS_RELAY_OWNER=none`. Существующие параметры WAHA и личных автоответов не менять. Развернуть выбранный релиз штатным `ops/deploy-stack.sh`; frontend тоже должен соответствовать релизу. Проверить `/health/live`, `/health/ready` и SHA.
5. Перезайти в приложение для новых прав. Настроить одну тестовую доверенную группу. Отправить сообщение с другого участника. Убедиться: один сигнал, правильный текст, источник и заказ; состояние «Ожидает обработки»; статусы не изменились.
6. Проверить неоднозначное сообщение, исключение `не готов`, повторную доставку; проверить доступ менеджера. Проверить правило автостатуса и его целевой статус.
7. Проверить `BACKEND_STATUS_AUTOMATION=true`. Установить `BACKEND_INBOUND_SIGNALS_RELAY_OWNER=in_process`, пересоздать backend штатным deploy. **Это запустит уже накопленную очередь**, сначала проверить её.
8. Новое контрольное сообщение: состояние «Действия выполнены», нужный статус заказа, шаги и аудит без дублей. WAHA должен оставаться `WORKING`; очередь личных ответов независима.

Откат: поставить владельца новой очереди `none` и пересоздать backend. Приём можно оставить включённым для диагностики или отключить новым флагом. Таблицы не удалять, старые статусы автоматически не восстанавливать. Флаг очереди не отменяет уже закоммиченные действия.

## Проверки разработки

Все тяжёлые команды на shared host запускать через `rtk-heavy-guard`, один worker.
`INBOUND_SIGNALS_DOCKER_TEST=true vitest run backend/src/modules/inbound-signals --maxWorkers=1` использует отдельную случайную схему в test PostgreSQL, без public fallback, удаляет её после теста.
`node tests/inbound-signals-browse.mjs` проверяет реальные React-компоненты на локальных API fixtures через изолированный browse; это не доказательство связи с живым WhatsApp.

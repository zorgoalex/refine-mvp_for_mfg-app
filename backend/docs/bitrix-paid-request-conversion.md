# Автоматическое преобразование оплаченной CRM-заявки

Первый подтверждённый положительный платёж (частичная предоплата тоже)
может автоматически преобразовать связанную CRM-заявку в производственный
заказ ERP. Это **не новая сделка и не новый заказ**: сохраняются ID и связь.

## Условия

- Обратная синхронизация включена, не dry-run, её owner — `in_process` либо
  реально работающий внешний worker; `none` автоматику не запускает.
- `BACKEND_BITRIX24_AUTO_CONVERT_PAID_REQUESTS=true` (по умолчанию false).
- Настроены активный служебный integration_service и начальные статусы заказа.
- Включена запись сроков: `BACKEND_ENABLE_DEADLINES=true`,
  `BACKEND_DEADLINES_READ_ONLY=false`. Общий обработчик уведомлений не требуется.
- Заявка активна, без конфликта синхронизации, с точной связью Deal → ERP.
- Есть минимум одна активная деталь либо позиция каталога товаров/услуг.
- Оплата подтверждена в Bitrix, сумма положительна, валюта KZT, дата корректна,
  платёжная система сопоставлена с типом оплаты ERP.
- Для виджета дополнительно проверяются права исходного сотрудника, его
  сопоставление, доступ к заказу и подтверждение переплаты. Служебная учётная
  запись не обходит эти проверки.

## Результат и ожидание

Номер заказа назначается автоматически. Если проекта нет — создаётся проект;
существующий проект можно использовать только для того же клиента и не в архиве.
Конвертация, сроки по уже заданным датам, первоначальный платёж, суммы,
аудит и события фиксируются одной транзакцией. При ошибке преобразование
откатывается, а полученная в Bitrix оплата не теряется.

Если не хватает позиций или других условий, причина видна в карточке входящей
заявки пользователям с финансовым доступом. Повторная сверка пробует снова.
Сохранение состава/заказа запускает адресную сверку ожидающей заявки;
восстановление команды виджета также повторяет попытку. Не надо повторно
создавать платёж в Bitrix. Отмена оплаты не превращает заказ обратно в заявку.

В Bitrix-аудите: `bitrix24.request_auto_conversion.waiting` и
`bitrix24.request_auto_conversion.completed`, с заказом, платежом и известным
автором статуса оплаты. Те же переходы записываются в transactional outbox.
Неизменная причина не порождает запись при каждом опросе.

## Обновление production

1. Обычный deploy backend/frontend с миграцией
   `172_bitrix_paid_request_conversion.sql`; runner содержит probe.
2. В существующий `services.backend.environment` основного Compose добавить:

```yaml
BACKEND_BITRIX24_AUTO_CONVERT_PAID_REQUESTS: ${BACKEND_BITRIX24_AUTO_CONVERT_PAID_REQUESTS:-false}
```

3. До включения проверить **все ранее оплаченные активные CRM-заявки**:
   они тоже могут преобразоваться при следующей сверке. Не включать флаг,
   если это нежелательно. Миграция сама ничего не преобразует.
4. После проверки установить флаг true в рабочем runtime `.env`, проверить
   итоговую Compose-конфигурацию без вывода секретов и пересоздать backend.
   Одного редактирования `.env` для запущенного контейнера недостаточно.
5. Проверить тестовую заявку с позицией и частичной оплатой: тот же ID заказа,
   один проект, один платёж, корректные суммы и запись completed в аудите.
   Повторная сверка не должна создавать дубликат.

Отключение: вернуть флаг false и пересоздать backend. Уже преобразованные
заказы не изменяются. Прямую/обратную синхронизацию и их owner не менять.
Никакой переустановки приложения Bitrix или новых REST bindings не требуется.
